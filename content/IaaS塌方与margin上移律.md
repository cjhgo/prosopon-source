## 1. 主线: 统计复用律 → 超卖的物理前提 `[演绎]`

超卖 (overcommit / oversell) 不是一个道德问题, 是一个**物理条件**问题。一句话:

> **超卖能成立, 当且仅当负载的 peak 不同步到达 —— 你卖出去的"逻辑容量"之和可以超过物理容量, 因为大家不会同时来兑现。超卖倍数 ∝ peak-to-mean 的间隙 (statistical multiplexing, 统计复用)。**

这个原理不是云计算发明的, 是电信世纪的老东西 (**statistical multiplexing / 统计复用**): 电话网 1000 条中继线只铺 100 路, 因为不会所有人同时讲电话; VoIP、TCP 带宽共享同理。云计算只是把它搬到 CPU/内存/存储上。

**作者的独立推导** (session 原话): "我有 24 个 CPU, 通过复用和抢占可以提供 16+16 的访问能力, 这是合理的调度手段" —— 他把这个叫**"逻辑超卖"**, 自己造了词。业界标准词就是**统计复用**。用标准词更精确, 且点出前提: **16+16 能兑现, 靠的是两个 16 不同时打满**。一旦同步打满 (峰值对齐), 超卖立刻穿帮。

- **调度 vs 超卖不是二分, 是一条谱系** (纠正 session 里"调度就是超卖吗"的二分预设):
  - 严格装箱 (bin-packing, request=limit, **不超卖**) → 分时复用 (cgroup shares) → request/limit 分离 (**k8s 显式帮你超卖**) → hypervisor overcommit ratio (vCPU:pCPU=4:1) → spot (**明码承认可能兑不了**)。
  - "合理调度"和"奸商超卖"**不是**这条谱系上的两个点, 而是**正交的另一根轴** —— 契约是否明码 (见 §4)。

## 2. 技术地基一: GPU 对 k8s 的三违背 + 抽象税 `[演绎]`

> 这一节是整份经济学分析的**承重地基**。它是演绎孤岛 (硬物理), 照用。来源: 作者 AI-infra 本行 + k8s 训练栈的结构分析。

**k8s (以及所有云调度) 的承重假设**: 资源池由**可切分、可超卖、相互独立、可弹性、近乎无状态**的单元组成; 装得越满越好 (utilization%); 挂了重调度即可。**大数据 (bigdata) 负载全部成立, 训练负载逐条破。**

| k8s 假设 | 大数据为何成立 | 训练为何破 |
|---|---|---|
| 资源**可切分** | CPU 有毫核 (millicore)、cgroup 限额 | GPU 是**整 device**, 无毫核; 切 MIG 就改 SM 分区、断 NVLink |
| 单元**相互独立** | node A/B 上的 task 互不相干 | **拓扑耦合**: node 内 NVLink、跨机 InfiniBand; collective 性能取决于"拿到哪几张卡、怎么连" |
| **可弹性**扩缩 | task 随资源加减 | **gang (帮派调度)**: N 张卡要么全给要么起不来; 部分分配 = 死锁 |
| **无状态/短命** | task 秒级, 状态在外部存储 | 有状态/长命: 一次 run 几天, 巨额 in-GPU 态; 重调度 = 丢几小时 |

**三违背的压缩形式**: **stateful (破无状态) · 拓扑耦合 (破可切分/独立) · gang + 重启贵 (破弹性)**。

**抽象税 (为什么超卖对 GPU 结构性不成立)** `[溯因, 但解释力极强]`:

> **每加一层抽象 (虚拟化、超卖、多租户) 的货币, 是花一点性能买一层便利。云计算整个能成立, 就是因为这笔交易划算 —— 藏掉硬件、卖 fungible 单元、超卖赚差价。但 GPU 训练/推理的产品本身就是性能 (FLOPS/带宽)。于是交易破产: 任何藏硬件的抽象层, 花掉的正是你来买的东西。你没有性能可以"花"去买抽象。**

推论: **GPU 的超卖不是碰巧难做, 是结构性不可做 —— 封它 = 毁它的价值**。这条推论是后面所有商业结论的根。

## 3. 超卖手段谱系: 云原生老兵的五维度花活 `[演绎: 照用]`

回答 session 里那个问题 —— "到底有哪些超卖手段? k8s 云原生老兵乐此不疲的花活儿?" 按**维度**切 (不按手段名, 因为多数花活是几维复合):

| 维度 | 手段举例 | 机制 |
|---|---|---|
| **A 空间 (subdivide)** | cgroup `cpu.shares` · 内存 balloon (VM 动态收放) · KSM (相同内存页合并) · thin provisioning (存储声明 1T 实分 200G) · hypervisor overcommit ratio (vCPU:pCPU 4:1~8:1) | 把一份物理切成 N 份逻辑 |
| **B 时间 (time-share)** | CPU 时间片 (µs 级切换) · 业务错峰 (白天电商/夜里 batch) · CronJob | 同一份物理在不同时段服务不同租户 |
| **C 契约 (SLO 分级)** | k8s QoS 三档: Guaranteed (不超卖) / **Burstable** (request<limit, 天然带超卖) / BestEffort (可随时 kill); on-demand / reserved / **spot** (-70% 但随时收回) | 用户配合超卖, 便宜 = 承诺弱 |
| **D 弹性 (mask overcommit)** | HPA (按流量水平伸缩) · VPA (right-sizing, 把 request 填虚的 pod 拽小) · Cluster Autoscaler (节点也弹) | 把超卖分散到时间上, 让长期均值 < 峰值承诺 |
| **E 兜底 (降级路径)** | OOMKill (按 QoS 挑 victim) · CPU throttle (不 kill 只拖慢) · Pod eviction (节点压力挪走) · spot 中断预告 (2~30s) | 兑不了时按契约降级, 不是 SLO 全线崩 |

作者那个 "24 → 16+16" 精确对应 **A + B + C 的复合**: cgroup 分权重 (A) + 时间片切 (B) + 承诺双份 request 但 limit 让它 burst (C), 再叠 D 的弹性, 让实际同时到达少于账面承诺。

**云厂商"把 k8s 封一层 k8s 卖给二级用户" —— 不是猜, 真的有** (纠正 session 里的"我猜"):
- **managed k8s** (EKS/GKE/华为 CCE): 底下是 VM —— 这是**层级**, 不是超卖。
- **vcluster / Kamaji / HyperShift**: 一个 host cluster 里塞 N 个租户的**虚拟 k8s 控制面**, 共享底层 kubelet —— 这才是真"k8s over k8s"。
- **serverless k8s** (Fargate / 阿里 ACK Serverless): 按 pod 计费, 底层 k8s 藏起来。

## 4. "合理调度" vs "奸商超卖" 的边界三判据 `[溯因]`

作者 session 里的直觉 ("超卖显然是奸商手段, 但我推导出的逻辑超卖是合理的") —— 这个直觉对, 但边界不在"超不超卖", 在**契约清晰度**。三条同时成立 = 合理:

1. **契约明码**: tier 分级 + 价格分级 + 中断预告。(spot 便宜 70% + 30 秒中断预告, 是"合理超卖"的教科书样本 —— 它没骗你, 明说了可能收回。)
2. **降级路径明确**: 兑不了时按契约 kill/throttle, 不是无差别地让所有人的 SLO 一起崩。
3. **统计前提真成立**: 租户不同步到达 peak, peak-to-mean 有充裕间隙。

**任一破坏就是奸商**: 偷偷把 overcommit ratio 拉到 12:1 不告知 (破 1) · SLO 无差别定价而底层已在 throttle (破 2) · 卖给一群恰好高度同步的租户 (破 3, 比如把"超卖 CPU"那套卖给一批同时跑训练的人)。

> **边界律**: 超卖本身价值中性; "奸商"与否取决于契约是否明码、降级是否可预期、统计前提是否真成立。**这三条恰好也是"能不能超卖"的物理条件的商业投影** —— 物理上没间隙 (§7 的 GPU) 时, 硬超卖必然破第 2、3 条, 所以 GPU 超卖天然滑向"奸商", 这不是道德堕落, 是物理逼的。

## 5. 关键分层: IaaS (卖资源) vs 应用层 (卖服务) —— 别混 `[演绎: 已考证 (被作者当场纠正)]`

> **这一节是整份笔记的枢纽, 也是作者当场抓住 agent 一个 cross-layer 混淆后逼出来的** (弯路详见 §11)。

老云计算厂商 (CPU 时代的 AWS) 同时做**两层生意**, 但这两层是**两种完全不同的超卖**:

| 层 | 卖什么 | CPU 时代例子 | 超卖机制 |
|---|---|---|---|
| **IaaS (基础设施即服务)** | 卖**资源** (裸算力), 不做应用 | EC2、裸 vCPU、块存储 | **cross-tenant** 统计复用 (A 家和 B 家的进程混跑同一物理机) |
| **PaaS / 应用层** | 卖**服务** (榨干自己的资源做成产品) | RDS、S3、Lambda、Aurora | 内部资源利用率优化 (不是把物理机租给多租户混跑) |

**作者的纠正 (原话精神)**: "你混淆了卖 API 的和卖 GPU 的。以前的云厂商是卖 CPU, 但他们不做应用。你例子里的 request 说的是卖 API 那一层干的活。"

—— 完全正确。agent 上一版拿 "vLLM 一张 H100 服务 200+ 并发 request" 当"GPU 超卖", 是**归错了轴**:
- 那 200 并发是**应用层内部把自己的 GPU 榨干**, 不是 IaaS 层把一张卡的租约超卖给 200 个不相干租户。
- 你调 OpenAI 的 API = **买应用/服务**, 不是在 IaaS 层和别人合租一张卡。

**这两件事在 CPU 时代都在 AWS 一家手里** (它既卖 EC2 也卖 RDS), 所以容易混。**在 GPU 时代, 这两层分裂了** —— 这个分裂就是 §7 的核心。

## 6. 两层 × 两时代: 超卖的完整矩阵 `[事实=演绎 / 框架=溯因]`

把 §5 的两层 × CPU/GPU 两时代铺开, 得到完整图景:

| | CPU 时代 | GPU 时代 |
|---|---|---|
| **IaaS 层 (卖资源)** | 花活满地: overcommit 4~8× · Burstable · request/limit · spot · Fargate · vCPU:pCPU 4:1 | **结构性塌方**: 整卡 on-demand + spot 就是全部。MIG 是**硬分区** (静态切死, 无"承诺>供给", 不算超卖); MPS 有 cross-tenant fault isolation 问题, **云厂商不敢卖给外人** |
| **应用层 (卖服务)** | AWS 卖 RDS/S3/Lambda | AI API 服务商 (OpenAI/Anthropic/百炼/Bedrock): **cross-request 深复用**是它们的家 |

**GPU 推理超卖 = 换了轴的"深"超卖** (这是 §11 弯路修正后的精确版):

| | CPU 超卖 | GPU 推理超卖 |
|---|---|---|
| 复用主体 | **cross-tenant** (租户之间) | **cross-request** (同一模型内的请求之间) |
| 统计前提"peak 不同步"成立在 | **用户维度** (不同租户不同时忙) | **request 维度** (请求到达时间不同、decode 长度差数量级、prefill 计算密集/decode 访存密集正好互补) |
| 跨 workload 混部 | 常态 (web+batch+DB 共节点) | **几乎不行** (训练+推理共卡 → MFU 崩) |
| 超卖的物理杠杆 | 时间片 + overcommit | **权重零边际成本** (一份 7B 权重占 14GB 固定, 服务几十上百 request, 剩余显存全用来装 KV cache) + **PagedAttention** (KV cache 按 4KB page 切, thin provisioning 的 GPU 版, 利用率从 20~40% → 90%+ `⚠️数字来自 PagedAttention/vLLM 原论文, 值得引用时重核`) |
| 天花板 | 4~8× 横向 | 单模型内 20~100× request 并发, **但 cross-tenant 那一维天然极窄** |

> **超卖轴切换律** `[溯因]`: **CPU 超卖是"广"超卖 (横向铺租户); GPU 推理超卖是"深"超卖 (一份权重纵向深度复用)。** 作者直觉"推理超卖没多少空间"精确成立于 **cross-tenant 那一维** (那维确实塌了); 但整体超卖倍数不塌, 只是**从横轴搬到了纵轴**。这解释了为什么云厂商的 GPU 推理产品都是 **serverless 单模型 endpoint** (Bedrock/SageMaker/百炼) 而非"多租户共卡" —— 它们把超卖从 cross-tenant 搬到 cross-request 收回来卖。

**"显存不可分所以超卖空间小" —— 半错半对** (session 里作者的 pushback, 值得单独澄清):
- **权重**不可分, 但**不需要分**: 一份权重服务 N 个 request 是**复用**, 是零边际成本的主杠杆, 根本不经过"分"这一步。CPU 那边没有这个东西。
- **KV cache** 恰恰**可分且已在分** (PagedAttention)。所以"显存不可分 → 超卖空间小"这一步逻辑掉链: 超卖分子里最大那块 (权重复用) 不经过"分"。
- **"推理不追 MFU 所以只是能用" —— 也半错**: 推理不叫 MFU, 但换了 KPI 追得一样狠 —— **tokens/s/$** (goodput per dollar)、**TTFT/ITL 延迟 SLA**、并发数。TensorRT-LLM/vLLM/SGLang 卷成什么样即证据。**换了 KPI, 不是没 KPI。**

## 7. 核心论题: IaaS 塌方 → margin 上移律 `[溯因]`

> 这是整份笔记的**经济学顶点**, 也是作者要的"上层商业行为分析"。是溯因论题, 不是可裁决事实。

**CPU 时代的利润结构**: 云厂商的 margin **藏在 IaaS 层的超卖里** —— overcommit 4:1 + spot, 租户天然不同步 → 卖出 4× 逻辑容量只付 1× 电费。应用层 (RDS 等) 是加分项, 但 IaaS 超卖是利润底盘。

**GPU 时代的利润结构** (抽象税 §2 在 IaaS 层刚性生效, 整卡=整卡, 无间隙可卖):

> **margin 上移律**: **当 IaaS 层的超卖空间被物理压到零, 利润无法在这一层产生, 于是 margin 被迫上移到应用层。谁能在应用层做出 cross-request 深复用, 谁就接住了从 IaaS 层掉落的利润。**

三个可观测的结果 (溯因预测, `⚠️经验判断, 具体 margin 数字待核实`):
1. **新玩家诞生的位置**: OpenAI/Anthropic 出现在"IaaS 拿不到 margin、于是上移到 API 层"的那个位置。**他们不是老云厂商** —— 老云厂商的护城河 (IaaS 超卖 know-how) 在 GPU 时代不构成优势。
2. **老云厂商被迫上移**: AWS 做 Bedrock、GCP 做 Vertex、Azure 做 Azure OpenAI、阿里做百炼 —— 因为在 GPU IaaS 那层只能收整卡租赁的辛苦费, 必须自己也做应用层服务商才有 margin。
3. **纯 GPU IaaS 玩家 (CoreWeave/Lambda) margin 结构性单薄**: 纯 IaaS 打法, 靠规模不靠超卖, 与 CPU 时代 AWS"超卖+规模"双重利润的商业模型**本质不同**。`⚠️CoreWeave/Lambda 的实际利润率与商业模型细节待核实, 这里只是从结构推出的方向性判断`

**这条律比"技术上 GPU 不能超卖"更根本**: 它从技术约束穿透到**利润在哪一层产生**, 进而决定**产业结构** (谁是新王、老王如何自救、谁被困在薄利层)。

## 8. 训练侧的再一次塌方: 连应用层都没有 `[演绎地基 / 溯因顶]`

推理侧 IaaS 塌了, 但应用层那半 (cross-request 深复用) 还立着。**训练侧连应用层那半都塌了。**

**演绎地基**: 训练是 gang + 有状态 + 全或无 (§2 三违背同时命中)。cross-request 复用需要"请求独立、短命、可穿插"; 训练的一个 job 就是一个巨大的、长命的、内部 rank 全或无耦合的整体 —— **没有"多请求"可供穿插**, cross-request 超卖也归零。

**溯因顶**: 于是训练**没有一个 SaaS 化的商业模型**, 只剩三条退路:
- **内部平台自用**: cybertron/LTP 这类 —— **成本中心, 不是利润中心**。
- **整机租赁 (卖 IaaS)**: CoreWeave 卖 8×H100 集群/月租, margin 薄。
- **Fine-tuning API** (LoRA/prompt-tuning): OpenAI/Anthropic 卖的那点, 本质仍是推理时加载适配器, **不是真正的 pretraining/full-SFT**。

> **训练侧 margin 无处可移律** `[溯因]`: 推理的 margin 能上移到应用层; 训练的 margin **上移到哪一层都上不去** (没有 SaaS 化产品可承接), 只能**留在自己的电费里内部消化**。这就是为什么全世界的大规模 pretraining 都在**自建平台内部**跑 (Meta/Google/OpenAI/字节/百川皆自建), 而非买一个"训练即服务"。

**焊回作者的 AI-infra 立场** (cross-repo 钩子): 这精确对应作者 LTP 立场文件里"公司自有机房/多云 → 必有自己的算力平台"那句 —— **不是公司的偏好选择, 是训练侧根本没有可对标的 SaaS 产品可买, 只能自建**。技术母题 (§2 三违背) 在这里穿透成了**产业组织结论** (为什么训练平台必然是 in-house 成本中心)。

## 9. 玩家三分: 谁赚钱、在哪层赚 `[溯因] ⚠️经验部分待核实`

把三种负载 × 两层利润画成产业地图 (方向性, 非精确财务):

| 负载 | IaaS 层能超卖吗 | 应用层能深复用吗 | margin 落在哪 | 典型玩家 |
|---|---|---|---|---|
| **CPU / 大数据** | ✅ 广超卖 (4~8×) | ✅ (RDS 等) | **IaaS 层为主** | 老云厂商 (AWS/阿里云) |
| **GPU 推理** | ❌ (整卡) | ✅ cross-request 深超卖 | **应用层** | API 服务商 (OpenAI/Anthropic) + 上移的老云厂商 (Bedrock/百炼) |
| **GPU 训练** | ❌ (整卡) | ❌ (gang, 无多请求) | **无处可落 → 内部电费** | 自建平台的大厂 (成本中心) + 薄利整机租赁 (CoreWeave) |

**三个负载对三违背的命中度不均匀** (这是整张地图的物理根, `[演绎]`):

| 违背 | CPU/大数据 | GPU 推理 | GPU 训练 |
|---|---|---|---|
| stateful | 破 (状态少, 可迁移) | 部分破 (KV cache 有状态但请求短命) | **全破** |
| 拓扑耦合 | 无 | 弱 (常单卡) | **强 (TP/EP 跨 rank)** |
| gang | 无 | 无 (请求独立) | **强 (collective 全或无)** |

> **训练是三违背同时命中的唯一战场, 也是超卖尺子唯一整根断掉、margin 唯一无处可移的战场。** 这一格的空 (没有训练即服务的 SaaS), 不是市场没成熟, 是物理结构不允许。

## 10. 迁移出去的尺子 (给未来 session 与跨域)

从这份具体分析里磨出、可迁移出云计算的判断装置:

- **统计复用律**: 任何"超卖/共享/复用"生意, 先问"peak 同步还是异步到达"。同步 → 超卖必骗; 异步 → 超卖是真本事。(可迁移到: 航空超售、餐厅翻台、保险精算、共享经济。)
- **抽象税刚性**: 当一个东西**的产品本身就是被抽象层花掉的那个货币**时, 抽象封装结构性不成立。(GPU 的货币是性能; 类比: 奢侈品的货币是稀缺性 —— 你不能靠"量产"来降本, 量产直接毁掉你卖的东西。)
- **margin 上移律**: 当某一层的利润机制 (这里是超卖) 被物理掐死, 利润不会消失, 会**上移到下一个能产生差异化的层**; 追踪"谁接住了上移的 margin"就能预测产业新王。
- **轴切换 (而非轴消失)**: "X 在这个维度不行了"常常不是 X 归零, 而是**换了一根轴**。推理超卖没在 cross-tenant 轴消失, 是搬到了 cross-request 轴。找到新轴, 而非宣布死亡。
- **分层再问一次**: 任何"这个东西能不能赚钱"的判断, 先剥出它在**哪一层** (IaaS/PaaS/应用)。同一个技术约束在不同层结论相反 (GPU 在 IaaS 塌方、在应用层繁荣)。—— 这条与本目录历史笔记的"**载体密度**要先剥离"同构: 都是"先分层/剥载体, 再比本体"。

## 11. [修正史] 两处弯路: 轴混淆 + 层混淆 (资产, 不删)

> 弯路是资产。这里记录 agent 在 session 中被作者 pushback 拆掉的两个观点, 供未来复用。

**弯路一: 轴混淆 (agent 第一版)**
- **agent 原持**: "GPU 推理超卖回来了" —— 把推理的 cross-request 复用当成和 CPU cross-tenant 超卖**同一根轴**, 举 "vLLM 200 并发" 为例, 暗示 GPU 也能像 CPU 那样超卖。
- **作者拆的点** (逻辑断 + 事实偏): "推理也没带来多少超卖空间吧? 请求有空闲零散, 但显存占用不可分, 只能说能用, 不像训练追 MFU。"
- **修正后**: 显存"不可分"半错 —— 权重不需分 (复用, 零边际)、KV cache 可分 (PagedAttention)。超卖没在推理消失, 是**从 cross-tenant 轴换到 cross-request 轴** (广超卖 → 深超卖)。作者的直觉对在"cross-tenant 那维塌了", 需修正在"整体倍数没塌, 换了轴"。→ 结晶为 §6 的**超卖轴切换律**。

**弯路二: 层混淆 (agent 第二版)**
- **agent 原持**: 修正弯路一后, 仍把 "vLLM 200 并发" 直接叫 "GPU 超卖", 隐含"云厂商把 GPU 超卖给多租户"。
- **作者拆的点** (概念混层, 最关键的一刀): "你混淆了卖 API 的和卖 GPU 的。以前云厂商卖 CPU, 但他们不做应用。你例子里的 request 是卖 API 那层干的活。"
- **修正后**: cross-request 复用是**应用层自己榨干自己 GPU**, 不是 **IaaS 层把卡的租约超卖给多租户**。这两层在 CPU 时代都在 AWS 一家手里所以易混; GPU 时代**分裂**了。→ 这一刀直接逼出了整份笔记的枢纽 §5 和核心论题 §7 (margin 上移律)。**没有这次 pushback, 就没有这份笔记的顶。**

> **元观察**: 两次弯路都是 agent"把一个新现象硬塞进旧类别" (先塞进 CPU 超卖的轴, 再塞进 IaaS 的层)。作者两次都用"这不是同一个东西"把它掰开。**分类的纪律 (barrier: 该切就切、该分层就分层) 是这里的真功夫** —— 与作者工程本行的 barrier/leaky 判断同构。
